What the agent can do in Do Computer, and what to add

An audit of every action a person can take in the web app, set against the tools the agent has. It ends with the tools to add, in the order to build them, and the decisions that are yours.

Written 8 October 2026 from the code on main (after PR #17).

3. What to add

Group A is what you asked for and comes first. Group B is small and can follow in any order.

A0 · first

A way for some actions to ask first by default

Today every ability is allowed until a person sets a rule (approvals.ts:160). Adding a machine costs money and adding a connector gives the agent new powers from an address it may have read on a web page, so both should ask first unless the person says otherwise. The other new actions below reuse this.

  • Give each entry in ABILITIES a default rule, and keep an explicit "allow" instead of deleting it (approvals.ts:381 and :418 delete a rule on allow).
  • New abilities: "Add and remove machines", "Add and change connectors", "Change its model and settings", "Make new agents". They appear on the Permissions page with the others.

Also needed by A1 and A2: the actor has to know the app's address, to hand a person a link. It is passed today only as a header for connector sign-in.

A1

Machines: add, remove, and help connect a person's own

New actions on the existing computers tool.

  • add with kind and name. Same checks as the app's "Add computer": a kind the deployment offers, not the built-in shell, at most 10 in a workspace. The machine is open to the workspace's agents, as it is from the app. A machine is only made at its provider when first used, so adding returns at once and the agent can work on it in its next call.
  • list also says which kinds can be added.
  • remove with name. Deleting a machine deletes everything on it, so I would limit it to machines this agent added, and have it ask every time whatever the rule says.
  • connect_own returns the one-line install command (curl -fsSL <app>/install.sh | sh) for the person to run on their computer. They still confirm the code at /pair; the agent cannot and should not do that part.

Where: extend ComputerDirectory with add and remove (apps/web/src/server/computer-directory.ts), reusing insertMachine, destroyMachine and tellWorkspace in server/computers.ts. To know which machines an agent added, dc_computers needs a column for the agent beside the person.

A2

Connectors: a connectors tool

  • list: each connector, whether it is on, connected, needs sign-in or failed and why, and how many tools it has.
  • add with name and url. If the server needs no sign-in, its tools are there from the agent's next step. If it does, the reply carries a sign-in link and the chat shows a "Sign in to …" card. When the person finishes, the agent is told in the chat, the way it is told when a computer request is answered.
  • reconnect, enable, disable, remove.

Three things need care:

  • Sign-in is tied to a person. The callback only accepts the user who started it (server/connectors.ts:80). From a tool, that is the person whose message the agent is answering.
  • Access tokens must not go through the chat. The form in the app takes an optional access token, but one typed into a chat stays in the transcript and in history. For a service that needs one, the agent should hand the person a link to the Connectors form with the name and address filled in.
  • To check: whether tools installed during a turn are offered to the model in that same turn (connectors.ts:376), or only from the next message.

Where: the tool calls the same Connectors methods the routes do (connectors.ts:229 onward). The host gives the actor a way to record the sign-in state in dc_oauth_states. The callback returns the person to the chat instead of the Connectors page.

B1

Automations: run now, and timezone

  • schedule run with id: what "Run now" does in the app. Useful right after creating one, to test it.
  • Let update take timezone. It is accepted on create and dropped on update (schedules.ts:520; UpdateScheduleRequest has no such field).
B2

Its own settings and cost: a settings tool

  • get: model, thinking level, the models on offer, what a message does while it is busy, timezone, and cost so far by model.
  • set: model, thinking, when busy, timezone. The same checks as the app (actor.ts:1222). Asks first by default, since a model change changes cost.

This lets "use a cheaper model from now on" or "how much have you cost me?" work in the chat.

B3

Make a new agent

agents create with a first message for it. The new agent appears in the workspace as an egg, gets the workspace's machine like any other, and the first message reaches it through the existing agent-to-agent conversation. Same limit as the app, 20 in a workspace. Asks first by default.

Where: add create to AgentDirectory (server/agent-directory.ts), reusing createAgent and provideFor.

B4

Knowing its way around the app

When the agent cannot do something, it should send the person to the right screen with a link. Today it has a few loose phrases ("under Automations", "Computers, in the workspace settings"). A short bundled skill, or a prompt section, listing the screens and their addresses would cover it: /a/<agent>/connectors, /automations, /skills, /permissions, /library, /computers, /profile, /settings, and the workspace settings.

Later

Smaller things

  • Library: bring back a deleted file or an older version; write a document when the agent has no machine.
  • Computers: open a machine to all agents or to chosen ones.
  • Rename the chat it is in.
  • A read-only list of who is in the team.

5. How it fits the code

  1. State the agent keeps itself (connectors, automations, skills, identity, settings): the new tool action calls the same method as the HTTP route in packages/agent/src/actor.ts, so the app and the agent cannot drift apart.
  2. State in the app's database (computers, agents): the agent reaches it through the directories the host passes in, ComputerDirectory and AgentDirectory. New actions are new methods there, with the same limits the routes apply.
  3. Only from a chat with a person. Sub-agents and scheduled runs are refused, as schedule and computers request already do (schedules.ts:480), so that there is someone to ask and somewhere for the answer to go.
  4. Who did it. Each change records the agent and the person whose message it was answering.
  5. The app updates itself. Each change sends the existing "changed" event (connectors, computers, schedules) or calls tellWorkspace, so open screens refresh.
  6. Cards in the chat. Tool results carry details, as subagent does, for a "Machine added" card and a "Sign in to …" card. These are new UI, so a mock-up in prototypes/ should come before the build.
  7. Tests. Each tool gets cases beside packages/agent/test/connectors.test.ts and machines.test.ts, and one end-to-end case each in apps/web/e2e/computers.spec.ts and connectors.spec.ts (the fake MCP server there already has a sign-in path).

Order: A0, then A1 and A2 (independent of each other), then B1, B2 and B4 in any order, then B3 if wanted.

6. Decisions for you

QuestionWhat I would do
Should adding a machine ask first?Yes by default, with the usual "always allow" on the card. You can set it to allow on the Permissions page.
May the agent delete machines?Only ones it added, and it asks every time.
How should a connector that needs a token be added?Never through the chat. The agent hands over a link to the form with the rest filled in.
May the agent change its own model?Yes, asking first, limited to the models the deployment offers.
May the agent make new agents?Your call. It is cheap to build and easy to leave out.
In a team, may any member's request make the agent add a machine or connector?Yes: any member can already do both in the app. The approval card goes to the person who asked.
